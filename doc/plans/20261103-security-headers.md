# セキュリティヘッダを付ける

## 目的

`20261101-improvement-backlog.md` の C4（セキュリティヘッダが無い）に対応する。

セキュリティヘッダは、サーバがレスポンスに付けて「このページをこう守って」とブラウザに指示するヘッダである。
このアプリのレスポンスには、今は1つも付いていない。
ブラウザは指示が無ければ何も制限しないので、下の各節に書く攻撃をブラウザ側で止められない。

## 決めたこと

- ヘッダは Laravel のミドルウェアで付ける。Caddy（FrankenPHP が中で使っている Web サーバ）の設定では付けない。CSP の nonce（後述）はリクエストごとに作る値で、アプリでしか作れない。テストで確かめられるのもアプリだけである
- CSP は最初からブロックするモードで入れる。違反を記録するだけの `Content-Security-Policy-Report-Only` で様子を見る段階は挟まない。記録を受け取る仕組みが無く、開発者は1人なので、本番に出す前に手元で確かめれば足りる
- HSTS は本番だけで付ける

## 付けるヘッダ

### クリックジャッキングを防ぐ：`X-Frame-Options` と CSP の `frame-ancestors`

**何が起きるか。**
悪意のあるサイトが、このアプリを `iframe` で自分のページに埋め込める。
`iframe` を透明にして、自分のボタンの上に重ねておく。
利用者は相手のサイトのボタンを押したつもりで、実際にはこのアプリの「アカウントを削除」などを押してしまう。
これをクリックジャッキングと呼ぶ。

**なぜ困るか。**
利用者はこのアプリにログインしたままなので、押された操作はそのまま本人の操作として通る。

**どうするか。**
`X-Frame-Options: DENY` を付ける。ブラウザは、このアプリのページを他のサイトの `iframe` に表示しなくなる。
同じ意味の CSP の `frame-ancestors 'none'` も付ける。こちらが今の標準で、`X-Frame-Options` は古いブラウザ向けに残す。

### XSS の被害を抑える：`Content-Security-Policy`

**何が起きるか。**
今は React が表示のたびにエスケープしているので、XSS の穴は見つかっていない。
それでも、将来の変更やライブラリの不具合で穴ができれば、攻撃者が入れたスクリプトがページ上で動く。

**なぜ困るか。**
動いたスクリプトは、ログイン中の利用者として何でもできる。ストックを書き換えたり、アカウントを消したりできる。

**どうするか。**
CSP（Content Security Policy）は、「このページで読み込んでよいのはここからだけ」をブラウザに伝えるヘッダである。
許可していないスクリプトは、ページに入り込んでもブラウザが動かさない。
このアプリが読み込むものは、すべて自分のドメインから配っている。そのため、基本は自分のドメイン（`'self'`）だけを許可する。

外部のドメインを許可しなくてよいことは、次のとおり確かめた。

- フォントは、`laravel-vite-plugin/fonts` がビルドのときに Google からダウンロードし、`public/build` に入れて自分で配っている。表示のときに Google のサーバへは取りに行かない
- Push 通知を Push サービス（FCM や Apple のサーバ）へ送るのは、サーバ側の scheduler である。ブラウザからは送らない
- ブラウザが Push を購読する処理は、ブラウザと Push サービスの間で行われる。ページの通信ではないので CSP の対象にならない

設定する値は次のとおり。

| 項目 | 値 | 意味 |
|---|---|---|
| `default-src` | `'self'` | 下で個別に決めないものは、自分のドメインだけ |
| `script-src` | `'self' 'nonce-…'` | スクリプトは自分のドメインのファイルと、nonce の付いたタグだけ |
| `style-src` | `'self' 'unsafe-inline'` | スタイルはページ内に書いたものも許す（理由は後述） |
| `img-src` | `'self' data:` | 画像は自分のドメインと、`data:` で埋め込んだもの |
| `font-src` | `'self'` | フォントは自分のドメインだけ |
| `connect-src` | `'self'` | `fetch` などの通信先は自分のドメインだけ |
| `object-src` | `'none'` | Flash などのプラグインは使わない |
| `base-uri` | `'self'` | `<base>` タグで相対 URL の基準を他のサイトに変えさせない |
| `form-action` | `'self'` | フォームの送信先は自分のドメインだけ |
| `frame-ancestors` | `'none'` | 上のクリックジャッキング対策 |

### スクリプトを nonce で許可する仕組み

ページの `<head>` には、Laravel が `<script>` タグを書き出している（`@vite` と `@viteReactRefresh`）。
`'self'` だけでは、ページ内に直接書かれたこれらのタグも止まってしまう。
かといって、ページ内のスクリプトをすべて許す `'unsafe-inline'` を足すと、攻撃者が入れたスクリプトも動いてしまい、CSP を付ける意味が無くなる。

そこで nonce を使う。
nonce は、リクエストのたびに作り直す使い捨ての乱数である。
CSP に `'nonce-abc123'` と書いておくと、ブラウザは `<script nonce="abc123">` のように同じ値を持つタグだけを動かす。
攻撃者は次のリクエストで使われる値を知りようがないので、入れたタグに正しい値を付けられない。

Laravel には、この仕組みが用意されている。
`Vite::useCspNonce()` を呼ぶと値が作られ、`@vite` と `@viteReactRefresh` が書き出すタグに自動で付く。
`@fonts` が書き出す `<style>` にも同じ値が付く。
CSP のヘッダには、`Vite::cspNonce()` で取り出した同じ値を書く。

Inertia は、ページのデータを `<script type="application/json">` に入れて渡している。
このタグはデータの入れ物で、スクリプトとして実行されない。CSP の対象外なので、nonce は要らない。

### スタイルに nonce を使わない理由

shadcn の部品が土台にしている Radix は、ポップオーバーやドロップダウンを出す位置を、要素の `style` 属性で決めている。
`style` 属性には nonce を付けられない。許可するには `'unsafe-inline'` を書くしかない。

ここで注意がある。
CSP の仕様では、`style-src` に nonce を1つでも書くと、`'unsafe-inline'` が無視される。
`<style>` タグのために nonce も足すと、Radix の `style` 属性が止まり、ポップオーバーが正しい位置に出なくなる。
そのため `style-src` には nonce を書かず、`'unsafe-inline'` だけにする。

スタイルを許したままでも、守りが大きく弱くなるわけではない。
スタイルを入れられてもできるのは見た目を変えることまでで、スクリプトのように利用者の操作を代わりに行うことはできない。

### 開発環境では Vite の開発サーバを許可する

`npm run dev` の間、ページは Vite の開発サーバ（`http://localhost:5173` など）からスクリプトとスタイルを読み込む。
ファイルを保存したときの変更は、WebSocket で受け取る。
本番と同じ CSP のままだと、これらがすべて止まって画面が出ない。

`Vite::isRunningHot()` は、開発サーバが動いているときに真を返す。
真のときだけ、`script-src`、`style-src`、`connect-src` に開発サーバの URL を足す。
URL は Vite が `public/hot` に書き出したものを読む。ポートは決め打ちしない。

### MIME スニッフィングを防ぐ：`X-Content-Type-Options`

**何が起きるか。**
ブラウザは、サーバが「これは画像です」と伝えたファイルでも、中身を見てスクリプトらしければスクリプトとして扱うことがある。
これを MIME スニッフィングと呼ぶ。

**なぜ困るか。**
将来、利用者がファイルをアップロードできるようになったとき、画像に見せかけたスクリプトが動くおそれがある。

**どうするか。**
`X-Content-Type-Options: nosniff` を付ける。ブラウザは、サーバが伝えた種類のとおりにだけ扱うようになる。

### URL が外部に漏れるのを防ぐ：`Referrer-Policy`

**何が起きるか。**
ページ内のリンクから外部のサイトへ移ると、ブラウザは移る前のページの URL をリファラとして相手に送る。

**なぜ困るか。**
URL のパスやクエリに、利用者に関わる情報が入っていると相手に渡る。
メール確認のリンクのように、URL そのものが鍵になるものもある。

**どうするか。**
`Referrer-Policy: strict-origin-when-cross-origin` を付ける。
外部のサイトには `https://stock.deployshelf.dev` までしか送らず、パスとクエリは送らない。
同じサイトの中では今までどおり全体を送るので、アプリの動きは変わらない。
これは今のブラウザの既定の動きと同じだが、ブラウザ任せにせず明示しておく。

### HTTP での接続を防ぐ：`Strict-Transport-Security`（HSTS）

**何が起きるか。**
利用者が `http://` でアクセスすると、最初の1回は暗号化されない通信になる。
Fly.io の設定（`force_https`）で `https://` に転送しているが、転送される前の1回は盗み見られうる。

**どうするか。**
`Strict-Transport-Security: max-age=31536000` を付ける。
これを一度受け取ったブラウザは、1年間このドメインに `http://` で接続しなくなり、最初から `https://` を使う。

本番のドメインの `.dev` は、ブラウザに最初から HSTS が組み込まれている（HSTS プリロード）。
そのため、今のドメインではこのヘッダで新しく防げることはほぼ無い。
ドメインを移したときに守りが抜けないよう、付けておく。

本番だけにするのは、開発環境で困るからである。
`http://localhost` でこのヘッダを受け取ると、ブラウザは同じ `localhost` で動く別のアプリにも `http://` で接続しなくなり、開けなくなる。

## 作業

### 1. ミドルウェアを作る

`app/Http/Middleware/SetSecurityHeaders.php` を作り、上のヘッダをレスポンスに付ける。

nonce は、次の処理へ渡す前（`$next($request)` を呼ぶ前）に `Vite::useCspNonce()` で作る。
ページの HTML はコントローラの中で組み立てられる。
後から作ると、`<script>` タグを書き出す時点で値がまだ無く、タグに nonce が付かない。

### 2. すべてのルートに通す

`bootstrap/app.php` で、`$middleware->web()` ではなく `$middleware->append()` に足す。
`append()` に足したミドルウェアは、すべてのリクエストに通る。

`web` グループに足すと、次のレスポンスにヘッダが付かない。

- `routes/pwa.php` のルート。マニフェストの取得でセッションを作らないよう、わざと `web` グループを通していない。`offline.html` もここから返している
- Laravel が例外から作るレスポンスの一部

`offline.html` は、ページ内に `<style>` を書いている。
`style-src` に `'unsafe-inline'` があるので、CSP が付いても表示は崩れない。

### 3. テストを書く

`tests/Feature/SecurityHeadersTest.php` で次を確かめる。

- 一般ユーザーの画面、管理画面、ログイン画面、エラー画面、`/app/offline.html` のすべてにヘッダが付く
- CSP に書いた nonce と、HTML の `<script>` タグの `nonce` 属性が同じ値になっている
- リクエストのたびに nonce が変わる
- HSTS は、本番の設定のときだけ付く

### 4. 実際のブラウザで確かめる

CSP で止めすぎると、テストは通っても画面が動かなくなる。
本番に出す前に、`npm run build` した状態と `npm run dev` の状態の両方で、次の画面を開く。
DevTools のコンソールに CSP の違反が出ていないことを確かめる。

- Chrome：ログイン、ダッシュボード（カレンダー、購入のダイアログ、インストールの案内）、ストック管理、Push 通知（ON にする操作も行う）、設定、管理画面
- iOS のホーム画面に追加した版：ダッシュボード、Push 通知

### 5. 設計書に写す

`doc/design/non-functional.md` の「セキュリティ」の表に、セキュリティヘッダの行を足す。

## ヘッダが付かないもの

FrankenPHP は、`public` にある静的ファイル（ビルド済みの JS、CSS、フォント、アイコン）を、PHP を通さずに直接返す。
ミドルウェアは PHP の中で動くので、これらのファイルにはヘッダが付かない。

困ることは無い。
CSP とクリックジャッキング対策が効くのは、ブラウザが表示する HTML のページだけである。
JS や CSS のファイルにヘッダを付けても、守りは変わらない。

## 追記（2026-11-03）：開発サーバは font-src と img-src にも足す

作業1で、開発サーバの URL を `font-src` と `img-src` にも足した。
開発中は CSS が開発サーバから読み込まれるので、CSS の中で指定したフォントや画像の URL も開発サーバを指す。
`script-src`、`style-src`、`connect-src` だけでは、開発中に和文フォントが当たらない。
