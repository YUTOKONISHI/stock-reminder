# ログイン状態を保持する

## 目的

`20261101-improvement-backlog.md` の B7 に対応する。

今は、操作しないまま120分たつとセッションが切れ、ログイン画面に戻される。
このアプリは、朝の通知を見て開き、購入を押して閉じる使い方を想定している。
開く間隔はたいてい2時間を超えるので、ほぼ毎回ログインを求められる。
ホーム画面から開く PWA でも、通知をタップした先がログイン画面になる。

ログイン画面で「ログイン状態を保持する」を選べるようにし、セッションが切れても自動でログインし直せるようにする。

## 決めたこと

- ログイン画面にチェックボックスを置き、初期値はチェックありにする
- 保持する期間は30日にする
- 設定画面でパスワードを変えたら、ほかの端末の保持を無効にする。変更した端末の保持は続ける

チェックありを初期値にするのは、端末を1人1台で使う前提だからである。
また、ホーム画面に追加した iOS の PWA は、Safari と cookie を共有しない。
初期値がチェックなしだと、PWA で入り直したときにチェックを忘れ、保持が効かないことが起きやすい。

30日にするのは、端末を盗まれたときに使われ続ける期間を区切るためである。
何も設定しなければ Laravel の既定の400日になる。
月に一度ログインし直す程度なら、使い心地への影響は小さい。

## 仕組み

チェックを入れてログインすると、Laravel はセッションの cookie とは別に、保持用の cookie（remember cookie）を発行する。
中身は「利用者ID｜`users.remember_token` の値｜パスワードハッシュから作った HMAC」で、APP_KEY で暗号化される。
セッションが切れた後のリクエストでこの cookie が届くと、Laravel は ID とトークンを DB と照らし合わせ、合えばその利用者でログインし直す。

cookie の守りは、セッションの cookie と同じ設定がそのまま効く。
JavaScript からは読めず（HttpOnly）、本番では HTTPS でしか送られず（`SESSION_SECURE_COOKIE=true`）、ほかのサイトからの POST には付かない（SameSite=Lax）。
DB の `remember_token` が漏れても、暗号化に APP_KEY が要るので cookie は作れない。

期限は発行した時点から数える。
使っても延びないので、30日たてば一度ログインし直すことになる。

サーバ側のログイン処理は、もともとこの仕組みに対応している。
Fortify のログイン処理は、リクエストの `remember` が真なら保持用の cookie を発行する。
`users` テーブルにも `remember_token` 列がある。
足りないのは、画面からの `remember` の送信と、期間の設定と、パスワード変更時の無効化である。

## 変えること

### ログイン画面

`resources/js/pages/auth/login.tsx` のパスワード欄の下に、「ログイン状態を保持する」のチェックボックスを置く。
フォームの初期値に `remember: true` を足す。

`resources/js/features/auth/api.ts` の `login()` は、受け取る値の型に `remember: boolean` を足す。
受け取った値をそのまま送っているので、送る処理は変えなくてよい。

### 保持する期間

`config/auth.php` の `web` ガードに `'remember' => 43200` を書く。
単位は分で、43200分が30日にあたる。
管理者の `admin` ガードは保持の仕組みを使っていないので触らない。

### パスワード変更

`ProfileController::update` は、パスワードを変えるとほかの端末のセッションを DB から消している。
ただ、保持用の cookie が残っていれば、その端末は次のリクエストで自動でログインし直してしまう。
cookie の中のトークンが DB の `remember_token` と合う限り、通ってしまうからである。

そこで、パスワードを変えるときに `remember_token` を新しい値に作り直す。
`UpdateUserPassword` でパスワードを保存するところに、`'remember_token' => Str::random(60)` を足す。
パスワード忘却からの再設定（`PasswordResetController`）でも同じ書き方で作り直している。

これだけだと、変更した端末の cookie も古いトークンのままになる。
セッションが切れた時点で、変更した本人までログイン画面に戻される。
今のパスワード変更は「ほかの端末は締め出し、今の端末は残す」という動きなので、それと食い違う。

そこで、変更した端末が保持用の cookie を持っていたら、新しいトークンで cookie を発行し直す。
`ProfileController::update` の最後で呼んでいる `$request->session()->regenerate(true)` を、次の書き方に置き換える。

```php
$guard = Auth::guard('web');
$guard->login($user, $request->hasCookie($guard->getRecallerName()));
```

なぜこれで動くか。
`login()` は、セッションの ID を作り直してからログイン済みの印を書き込む。
今の `regenerate(true)` と同じく、古いセッションは捨てられる。
第2引数が真のときは、利用者の今の `remember_token` で cookie を発行する。
直前に作り直したトークンが `$user` に入っているので、新しいトークンの cookie になる。

cookie を持っていたかどうかは、リクエストに保持用の cookie が付いているかで調べる。
`$guard->viaRemember()` は「このリクエストで cookie を使ってログインし直したか」を返すだけで、セッションがまだ生きているときは偽になるので使えない。

## 変わらないこと

ログアウトすると、その利用者の保持はすべての端末で無効になる。
Laravel のログアウトは `remember_token` を作り直し、トークンは利用者ごとに1つしかないからである。
PC とスマホの両方を使う人は、片方でログアウトすると、もう片方もセッションが切れた後にログインし直すことになる。
1人1台の前提なので、このままにする。

画面を2時間以上開いたままにしてから送信すると、今と同じく419になる。
保持用の cookie でログインし直す前に、CSRF トークンの照合で弾かれるためである。
これは保持の仕組みでは直らない。
419の扱いは `20261103-error-pages.md` で決めている。

## テスト

`tests/Feature/LoginTest.php` に足す。

- `remember` を真にしてログインすると、保持用の cookie が発行され、期限が30日後になる
- `remember` を偽にしてログインすると、保持用の cookie は発行されない
- セッションが無くても、有効な保持用の cookie があればダッシュボードを開ける

`tests/Feature/ProfileControllerTest.php` に足す。

- パスワードを変えると `remember_token` が変わる
- 保持用の cookie を付けてパスワードを変えると、新しいトークンで cookie が発行し直される
- 保持用の cookie を付けずにパスワードを変えると、cookie は発行されない
- 名前だけを変えたときは `remember_token` が変わらない

ログイン画面のテスト（`resources/js/pages/auth/login.test.tsx`）を作る。

- チェックボックスが最初からチェックされている
- 送信すると `remember` が送られる
