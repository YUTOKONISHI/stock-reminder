# 一般ユーザーのログインに2段階認証を入れる

## 目的

Issue #50 に対応する。

今は、メールアドレスとパスワードが分かれば誰でもログインできる。
パスワードを使い回している人は、ほかのサービスから漏れたパスワードでそのまま入られてしまう。

そこで、スマホの認証アプリ（Google Authenticator など）に表示される6桁のコードを、パスワードの次に入力させる仕組みを入れる。
この方式を TOTP と呼ぶ（時刻をもとに30秒ごとに変わるコードを作る方式）。
パスワードが漏れても、本人のスマホが無ければログインできない。

## 決めたこと

- 方式は TOTP にする。Fortify に機能があり、パッケージを足さずに作れる
- 任意にする。設定画面から本人が有効にした人だけ、ログインのときにコードを求める
- 認証アプリの端末もリカバリーコードもなくした人は、管理者が artisan コマンドで2段階認証を外す
- 2段階認証が外れたら、登録しているメールアドレスへ知らせる
- 管理者の連絡先は画面に出さない。コード入力画面から解除を依頼でき、依頼は `ADMIN_ALERT_EMAIL` へメールで届く
- パスワード忘却からの再設定では、2段階認証を外さない

任意にするのは、主な利用者が使い心地を重視するからである。
必須にすると、認証アプリを知らない人が登録の途中でやめてしまう。

パスワード忘却からの再設定で外さないのは、再設定がメールを受け取れるだけで通るからである。
そこで外すと、メールを乗っ取った人がパスワードも2段階認証もまとめて突破できてしまう。

管理者が外す手段を残すのは、スマホの機種変更や紛失で締め出された人を救うためである。
管理画面には利用者の一覧が無いので、画面は作らずコマンドにする。
外したことは登録アドレスへメールで知らせるので、本人以外の依頼で外してしまっても本人が気づける。

## 仕組み

### コードが合う理由

有効にするとき、サーバは利用者ごとにランダムな秘密の文字列を作る。
これを QR コードにして画面に出し、利用者が認証アプリで読み取る。
以後、サーバと認証アプリは同じ秘密の文字列と今の時刻から、同じ6桁のコードを計算する。
通信していないのにコードが一致するのはこのためである。

秘密の文字列は `users.two_factor_secret` に、APP_KEY で暗号化して保存する。
時計のずれに備え、前後30秒のコードまでは受け付ける（Fortify の既定）。
一度通ったコードは同じ30秒の間でも再び使えない（Fortify がキャッシュに記録して弾く）。

### リカバリーコード

認証アプリが使えないときのために、使い捨てのリカバリーコードを8個発行する。
コードの代わりにこれを入力すればログインでき、使ったものは新しい1個に入れ替わる。
`users.two_factor_recovery_codes` に暗号化して保存する。

### 有効になるまでの2段階

Fortify の `confirm` オプションを有効にしているので、有効化は2段階で進む。

1. 「有効にする」を押すと、秘密の文字列とリカバリーコードが作られる。この時点ではまだログインでコードを求めない
2. 認証アプリに出たコードを入力して合えば、`two_factor_confirmed_at` に時刻が入り、ここから求めるようになる

2段階にするのは、QR コードを読み取り損ねたまま有効になり、本人が締め出されるのを防ぐためである。

### ログインの流れ

1. ログイン画面でメールアドレスとパスワードを送る
2. パスワードが合い、2段階認証が有効なら、まだログインさせない。利用者IDと「ログイン状態を保持する」の選択をセッションに置き、コード入力画面へ送る
3. コード入力画面でコードかリカバリーコードを送る。合えばここで初めてログインする
4. 保持を選んでいれば、このとき保持用の cookie を発行する

保持用の cookie でログインし直すときは、コードを求めない。
保持の期限（30日）が切れて入り直すときに、再び求めることになる。

## 変えること

### User モデル

`App\Models\User` に Fortify の `TwoFactorAuthenticatable` トレイトを付ける。
このトレイトが、QR コードの生成やリカバリーコードの読み書きを持っている。

`#[Hidden]` に `two_factor_secret` と `two_factor_recovery_codes` を足す。
今は全画面に `auth.user` として利用者の行をそのまま載せているので、隠さないと暗号化された秘密の文字列が画面の HTML に入る。
暗号化されていても、外に出す理由が無い。

`two_factor_confirmed_at` は隠さず、`casts()` に `datetime` を足す。
画面で「有効かどうか」を出すのに使う。

### ログインの流れ

`FortifyServiceProvider` の `authenticateThrough` で、`AttemptToAuthenticate` の前に2段階認証の分岐を入れる。

Fortify が用意している `RedirectIfTwoFactorAuthenticatable` は、パスワードが違ったときに `email` キーで英語のエラーを返す。
今のログイン画面は `auth_error` キーで「名前またはパスワードが正しくありません」を出しているので、このままだと文言と出る場所が変わる。
そこで `App\Actions\Fortify\RedirectIfTwoFactorAuthenticatable` を作って Fortify のものを継承し、失敗時の例外だけを差し替える。
中身は今の `AttemptToAuthenticate` の差し替えと同じにする。

パイプラインには、この自前のクラスを入れる。
`redirectUserForTwoFactorAuthenticationUsing` の指定も自前のクラスに変える。

パスワードの照合は、分岐のクラスと `AttemptToAuthenticate` で2回行われる。
Fortify の既定の流れと同じなので、そのままにする。

### コード入力画面

`Fortify::twoFactorChallengeView` で、Inertia のページ部品 `auth/two-factor-challenge` を返す。
URL は `/app/two-factor-challenge` で、ルートは Fortify がもう登録している。

画面には6桁のコードの入力欄を1つ置く。
「リカバリーコードを使う」のリンクで、リカバリーコードの入力欄に切り替える。
送る値の名前は、コードなら `code`、リカバリーコードなら `recovery_code` にする（Fortify が決めている）。

コードの入力欄には `inputmode="numeric"` と `autocomplete="one-time-code"` を付ける。
スマホで数字のキーボードが出て、iOS では候補にコードが出ることがある。

画面の下に「認証アプリもリカバリーコードも使えない場合」のリンクを置き、解除の依頼フォームを開く（後述の「解除の依頼」）。

送信の回数制限は、もう定義してある `two-factor` リミッタ（ログイン中の利用者ごとに毎分5回）が効く。

### パスワード確認画面

2段階認証の設定を変えるときは、直前にパスワードを入れ直させる（`config/fortify.php` の `confirmPassword` が有効）。
スマホを置いたままにしたとき、ほかの人に勝手に外されないようにするためである。
一度入れれば3時間（`config/auth.php` の `password_timeout`）は聞かれない。

`Fortify::confirmPasswordView` で、ページ部品 `auth/confirm-password` を返す。
パスワードの入力欄を1つ置き、`/app/user/confirm-password` に送る。
合えば、Fortify が元の画面へ戻す。

### 2段階認証の設定画面

設定画面のメニューに「2段階認証」を足し、`/app/settings/two-factor` の画面を作る。
ルートは `auth` と `verified` のグループに入れ、`password.confirm` ミドルウェアを掛ける。
`TwoFactorController::show` がページ部品 `settings/two-factor` を返す。

画面を開く時点でパスワードを確認させるのは、この画面にリカバリーコードを載せるからである。
もう一つ、確認の戻り先の都合もある。
確認を求められたとき、Laravel は確認後の戻り先を記録する。
GET の画面なら、その画面の URL が記録される。
POST のボタンで初めて求められた場合は、直前に見ていた画面の URL が記録される（POST の URL へは戻れないため）。
どちらでもこの設定画面に戻ってくるので、ボタンを押し直せば続きができる。

画面の状態は3つあり、コントローラが渡す値で切り替える。

| 状態 | 条件 | 画面に出すもの |
|---|---|---|
| 無効 | `two_factor_secret` が空 | 説明と「有効にする」ボタン |
| 設定中 | 秘密の文字列はあるが `two_factor_confirmed_at` が空 | QR コード、手入力用の文字列、コードの入力欄、「やめる」ボタン |
| 有効 | `two_factor_confirmed_at` がある | 有効であること、リカバリーコードの表示と作り直し、「無効にする」ボタン |

QR コードは `$user->twoFactorQrCodeSvg()` が SVG の文字列で返すので、設定中のときだけ値に入れて渡す。
Fortify には QR コードを JSON で返すルートもあるが、Inertia の値で渡せば画面から別に取りに行かなくて済む。
手入力用の文字列は、QR コードを読み取れない人のために出す（`decrypt($user->two_factor_secret)`）。

リカバリーコードは `$user->recoveryCodes()` で、有効のときだけ渡す。
有効にした直後は開いた状態で出し、「どこかに控えてください。スマホをなくしたときに使います」と添える。
それ以外のときは「表示する」を押したときだけ出す。

ボタンが送る先は、Fortify がもう登録しているルートを使う。

| 操作 | 送り先 |
|---|---|
| 有効にする | `POST /app/user/two-factor-authentication` |
| コードを確かめる | `POST /app/user/confirmed-two-factor-authentication` |
| やめる、無効にする | `DELETE /app/user/two-factor-authentication` |
| リカバリーコードを作り直す | `POST /app/user/two-factor-recovery-codes` |

これらは Inertia から送ると、成功すれば元の画面へ戻り、画面の値が読み直される。
コードが違ったときは `code` キーにエラーが入るので、入力欄の下に出す。
送る処理は `resources/js/features/auth/api.ts` に、ほかの認証まわりと並べて足す。

### 無効にしたときのメール

2段階認証が外れたら、`TwoFactorDisabled` 通知を登録アドレスへ送る。
文面は「2段階認証が無効になりました。心当たりが無ければパスワードを変更し、設定画面から有効にし直してください」とする。

Fortify には無効にしたときのイベントがあるが、設定中に「やめる」を押したときにも出る。
有効になっていない段階で「無効になりました」と送るのはおかしい。
そこで Fortify の `DisableTwoFactorAuthentication` を継承したクラスを作り、外す前に `two_factor_confirmed_at` が入っていたときだけ通知する。
`FortifyServiceProvider` の `register` で、Fortify のクラスをこのクラスに差し替える（サービスコンテナの `bind`）。
Fortify のコントローラはこのクラスを引数で受け取っているので、差し替えるだけで設定画面からの無効化にも効く。

### 解除の依頼

管理者の連絡先を画面に出すと、ログイン前の画面なので誰でもそのアドレスを読めてしまう。
そこで連絡先は出さず、コード入力画面から依頼を送れるようにする。

フォームにはメールアドレスの入力欄と送信ボタンを置く。
送り先は新しく作る `POST /app/two-factor-challenge/recovery-request` で、`TwoFactorRecoveryRequestController` が受ける。

この画面に来られるのは、パスワードが合った人だけである。
サーバはセッションの `login.id` で、誰がパスワードを通ったかを知っている。
入力されたメールアドレスがその利用者のものと一致したときだけ、次の2通を送る。

- `ADMIN_ALERT_EMAIL` へ、`TwoFactorRecoveryRequested` 通知。利用者ID、メールアドレス、依頼の日時、IPアドレスを書く
- 本人の登録アドレスへ、`TwoFactorRecoveryRequestReceived` 通知。「解除の依頼を受け付けました。管理者からこのアドレスに確認のメールを送ります。心当たりが無ければパスワードを変更してください」と書く

本人へも送るのは、パスワードを知った別人が依頼したときに、本人が気づけるようにするためである。

`login.id` がセッションに無い（パスワードを通っていない、またはセッションが切れた）ときは、ログイン画面へ戻す。
メールアドレスが一致しないときは、入力欄に「ログインに使ったメールアドレスを入力してください」と出す。
この人はパスワードを通っているので、一致しないと伝えても新しく漏れる情報は無い。

送れたら、「管理者に依頼しました。登録しているメールアドレスに連絡が届きます」と画面に出す。
同じ利用者からの依頼は1時間に1回までとする（`login.id` ごとのリミッタ）。
管理者へのメールが大量に届くのを防ぐためである。

### 管理者による解除

管理者は依頼のメールを受けたら、利用者の登録アドレスへ確認のメールを送る。
本人から返信があれば、本人の依頼とみなして次のコマンドで外す。

artisan コマンド `app:disable-two-factor {email}` を作る。
メールアドレスで利用者を引き、上の差し替えたクラスで2段階認証を外す。
同じクラスを通すので、本人へのメールもここで送られる。
利用者が居ないときは、エラーを出して終える。

外した後は、パスワードだけでログインできるようになる。
もう一度使いたければ、本人が設定画面から有効にし直す。

### リクエストログの伏せ字

`LogRequest` の伏せる項目に `code` と `recovery_code` を足す。
リカバリーコードは使えばすぐ入れ替わるが、使う前にログから読まれれば1回分ログインに使える。

### 日本語の文言

Fortify はコードが違ったときの文言を英語で返す（`__()` で翻訳できる形）。
`lang/ja.json` を作り、次の2つを訳す。

- The provided two factor authentication code was invalid. → 認証コードが正しくありません
- The provided two factor recovery code was invalid. → リカバリーコードが正しくありません

## 変わらないこと

パスワード忘却からの再設定と、設定画面でのパスワード変更は、2段階認証に触れない。
変えた後も、有効な人はログインのときにコードを求められる。

アカウントを削除すると、2段階認証の値は `users` の行と一緒に消える。

管理者のログインには入れない。
管理者は1人で、`admin` ガードは Fortify を通っていないからである。

テーブルは変えない。
`two_factor_*` の3列は、Fortify を入れたときのマイグレーションでもう作られている。

## テスト

`tests/Feature/TwoFactorLoginTest.php` を作る。

- 有効な利用者がパスワードでログインすると、ログインされずにコード入力画面へ送られる
- 正しいコードを送るとログインでき、ダッシュボードへ進む
- 違うコードを送ると、`code` にエラーが入り、ログインされない
- リカバリーコードでログインでき、使ったコードは入れ替わる
- 設定中（確認前）の利用者は、パスワードだけでログインできる
- パスワードが違うときは、今と同じく `auth_error` にエラーが入る
- ログイン画面で保持を選んでいれば、コードを通った後に保持用の cookie が発行される

`tests/Feature/TwoFactorSettingsTest.php` を作る。

- パスワードを確認していないと、設定画面を開くとパスワード確認画面へ送られる
- 3つの状態で、渡す値が切り替わる（設定中だけ QR コード、有効のときだけリカバリーコード）
- 有効にしてからコードを確かめると、`two_factor_confirmed_at` が入る
- 有効な状態から無効にすると、`TwoFactorDisabled` が送られる
- 設定中に「やめる」を押しても、`TwoFactorDisabled` は送られない
- `auth.user` に `two_factor_secret` と `two_factor_recovery_codes` が載らない

`tests/Feature/TwoFactorRecoveryRequestTest.php` を作る。

- パスワードを通った後に正しいメールアドレスで送ると、管理者と本人へそれぞれ通知が送られる
- メールアドレスが一致しないと、エラーが入り、通知は送られない
- セッションに `login.id` が無いと、ログイン画面へ戻され、通知は送られない
- 1時間以内に2回目を送ると、回数制限で弾かれる

`tests/Feature/DisableTwoFactorCommandTest.php` を作る。

- コマンドで外すと、3列が空になり、`TwoFactorDisabled` が送られる
- 居ないアドレスを渡すと、失敗の終了コードで終わる

`LogRequest` のテストに、`code` と `recovery_code` が伏せられることを足す。

画面のテストを作る。

- `auth/two-factor-challenge`：リカバリーコードの入力に切り替えると、送る値の名前が変わる
- `settings/two-factor`：3つの状態でそれぞれのボタンが出る
