# 朝の通知を送り損ねても取り戻す

## 目的

Issue #41（`20261101-improvement-backlog.md` の B5）に対応する。

朝の通知は、毎日9時に1回だけ送っている。
この1回を逃すと、その日の通知は届かず、誰もそれに気づけない。
逃し方は次の3つがある。

- 定時処理を動かすプロセス（Fly の `scheduler`）が落ちている、または固まっている
- デプロイや再起動が9時をまたぎ、9時の回が動かなかった
- 回は動いたが、一部の利用者の処理が失敗した

外部の監視サービスで「逃したこと」に気づけるようにする案も検討した。
ただ、気づいた後は結局手で送り直すことになり、通知のためだけに監視サービスを足すのは規模に合わない。
そこで、逃しても次の回で自分で取り戻せるようにし、失敗したときは管理者にメールで知らせる。

サービス全体とバックアップの監視は、この計画では扱わない。
外部の監視サービスが役に立つのはそちらなので、別の Issue に切り出す。

## 決めたこと

- 9時から12時まで、1時間ごとに送る（9時、10時、11時、12時の4回）
- その日の通知履歴がすでにある利用者には送らない
- 1人でも処理に失敗した回は、管理者にメールを送り、コマンドは失敗として終える
- 管理者のメールアドレスは設定値で持つ。空なら送らない

## 1時間ごとに送り、送り済みの人は飛ばす

### 何が起きているか

`scheduler` のプロセスは、毎分起きて「今この分に動かすものがあるか」を見ている。
9時0分に動けなかった回は、後から動かし直すことはない。
`fly.toml` の `restart = always` で、落ちたプロセスは起こし直されるが、起きたときにはもう9時を過ぎている。

### どうするか

`routes/console.php` のスケジュールを、9時の1回から、9時から12時までの毎時0分に変える。

```php
Schedule::command('app:send-purchase-reminders')
    ->hourly()
    ->between('9:00', '12:00')
    ->timezone('Asia/Tokyo')
    ->onOneServer();
```

`between` は両端を含むので、12時の回も動く。

このままだと、9時に送った人に10時以降も同じ通知が届いてしまう。
そこで `SendPurchaseReminders` は、ストックを集めた後で、今日（日本時間）作られた通知履歴がある利用者を外す。
「今日」は `created_at` が今日の0時以降であることで判定する。
通知履歴は送るたびに1件積むので、履歴があることを「今日はもう送った」の印に使える。
既読にしても行は消えないので、既読にした人に送り直すことはない。

### これで取り戻せるもの

- 9時の回が動かなかった日は、10時以降の最初の回で全員に送る
- 1人分の処理が失敗して履歴が作られなかった人は、次の回で送り直す
- `scheduler` が固まった場合は、取り戻せない。固まったプロセスはどの回も動かさないからである。まれな止まり方なので、この計画では扱わない

### 取り戻さないもの

Push の送信に失敗しても、通知履歴は積む（`doc/design/notification.md` の「送信の経路」）。
そのため、Push の送信だけが失敗した人は「送り済み」として扱い、次の回で送り直さない。
送信の失敗は、購読の期限切れなど、1時間後に送り直しても同じ結果になるものが多い。
履歴は Push通知画面で見られるので、このままにする。

### 変わる動き

9時より後に、予定日が今日以前になったストックを持つ人にも、その日の次の回で通知が届くようになる。
たとえば10時半にストックを登録して予定日が今日になった人には、11時に通知が届く。
9時に通知を受けた人は、その日のうちに予定日が来るものが増えても、もう一度は送らない。

## 失敗したら管理者にメールで知らせる

### 何が起きているか

`SendPurchaseReminders` は、利用者ごとの処理を例外ごと受け止め、ログに書いて次の人へ進む。
最後は必ず `SUCCESS` を返す。
ログは Fly の標準エラー出力に流れるだけなので、誰かが読みに行かない限り、失敗に気づけない。

### どうするか

コマンドの中で、失敗した利用者の数を数える。
数えるのは、今ログを書いている2か所（通知を積めなかった、利用者の処理ができなかった）である。

回の終わりに1人でも失敗していれば、次の2つを行う。

1. 管理者のメールアドレスへ、失敗した人数と、その回で対象にした人数を書いたメールを送る
2. コマンドは `FAILURE` を返す

メールは新しい通知クラス（`PurchaseRemindersFailed`）で送る。
管理者はメールアドレスを持たないので、宛先は `Notification::route('mail', ...)` で直接渡す。
メールの送信に失敗しても、ログに書いて終える。
知らせるための処理で、送り直しの処理を止めないためである。

失敗が続くと、1日に最大4通（9時から12時の各回）のメールが届く。
同じ原因でも回ごとに知らせることになるが、1日に4通なら気づくきっかけとして困らない量なので、まとめる仕組みは作らない。

### 管理者のメールアドレス

`config/services.php` に `admin.alert_email`（環境変数 `ADMIN_ALERT_EMAIL`）を足す。
本番では `fly secrets set` で置く。
`fly.toml` はリポジトリに入っており、アドレスを書くと公開されてしまうためである。
値が空のとき（開発環境やテスト）は、メールを送らずにログだけを書く。

## テスト

`tests/Feature/SendPurchaseRemindersTest.php` に足す。

- 今日の通知履歴がある利用者には送らず、履歴も増やさない
- 昨日の通知履歴しか無い利用者には送る
- 1人でも失敗した回は、管理者のアドレスへ失敗した人数を書いたメールを送り、コマンドが失敗で終わる
- 全員成功した回は、メールを送らない
- 管理者のアドレスが空なら、失敗してもメールを送らない

「通知の失敗」の既存の2件は、`assertSuccessful()` を `assertFailed()` に変える。
どちらも失敗が起きる場面なので、新しい決まりでは失敗で終わるのが正しい。

スケジュールは、時刻を9時前後と12時前後に固定して読み込み直し、9時から12時の毎時だけ動くことを確かめる。
`schedule:list` は `between` の絞り込みを表示せず、毎時（`0 * * * *`）としか出ないので、これでは確かめられない。
