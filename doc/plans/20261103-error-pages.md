# エラー時の画面と通信失敗の案内を整える

`20261101-improvement-backlog.md` の B6（#42）に対応する。

## できあがりの姿

作業が終わると、次の2つが変わる。

1つ目は、エラーの画面である。
今は、ページが無いときやサーバで失敗したときに、Laravel が最初から持っている英語の画面が出る。
これを、アプリと同じ色と文字の日本語の画面に変え、「ダッシュボードへ戻る」などのボタンを置く。
デザインは Claude Artifact の「エラー画面のデザイン案」にある。

| 起きたこと | ステータスコード | 画面の見出し | ボタン |
|---|---|---|---|
| 開く権限が無い | 403 | このページは開けません | ダッシュボードへ戻る |
| ページが無い | 404 | ページが見つかりません | ダッシュボードへ戻る |
| 画面を長く放置してから送信した | 419 | ページの有効期限が切れました | 読み込み直す、ダッシュボードへ戻る |
| サーバの中で失敗した | 500 番台 | 問題が発生しました | 読み込み直す、ダッシュボードへ戻る |

「読み込み直す」は、やり直せば直る見込みがある 419 と 500 番台にだけ置く。

2つ目は、サーバに届かなかったときの案内である。
今は何も表示されないので、電波が無い所で購入を記録すると、ボタンを押しても何も起きないように見える。
これを、画面の上に「通信できませんでした」というトーストを出すように変える。
入力した内容は残すので、電波が戻ったらもう一度押せばよい。

## 仕組みのあらまし

エラー画面は、次の流れで出る。

1. サーバでエラーが起きる
2. `bootstrap/app.php` がエラーを受け取り、エラー画面のページコンポーネントとステータスコードを返す
3. ブラウザ側で `resources/js/pages/error.tsx` が、ステータスコードに合った見出しとボタンを描く

通信失敗の案内は、次の流れで出る。

1. ボタンを押して送信したが、サーバに届かない
2. 画面の切り替えを受け持つ Inertia が `networkError` イベントを発火する
3. `resources/js/app.tsx` がそのイベントを受け取り、トーストを出す

## 作業の順番

### 1. ブランチを切る

`main` から作業用のブランチを切る。
この計画書も、そのブランチでコミットする。

### 2. エラー画面のページコンポーネントを作る

触るファイルは `resources/js/pages/error.tsx`（新規）と `resources/js/pages/error.test.tsx`（新規）。

props でステータスコードを受け取り、上の表のとおりに見出し、説明、アイコン、ボタンを出すコンポーネントを作る。
見た目はデザイン案に合わせる。

ログイン後の画面の共通の枠（`AppShell`）は使わない。
404 はログインしていない人にも出るので、ログイン後のメニューを並べると、押した先でログインを求められてしまう。

「ダッシュボードへ戻る」の行き先は、今の URL が `/admin/` で始まれば管理画面のダッシュボード、それ以外なら一般ユーザーのダッシュボードにする。
ログインしていない人が一般ユーザーのダッシュボードを開くとログイン画面へ送られるので、それ以上の分岐はいらない。

テストでは、ステータスコードごとに見出しとボタンが変わることと、URL で戻り先が変わることを確かめる。
この時点ではサーバとつながっていないので、ブラウザでは見られない。

### 3. サーバからエラー画面を返す

触るファイルは `bootstrap/app.php` と `tests/Feature/ErrorPageTest.php`（新規）。

`bootstrap/app.php` には、エラーの扱いを書く場所（`withExceptions`）がある。
そこに「403、404、419、500 番台のときは、手順2のページコンポーネントを返す」処理を足す。
1か所に書くので、どの画面で起きたエラーも同じように扱われる。

開発中（`.env` の `APP_DEBUG` が `true`）は、今までどおり Laravel の詳しいエラー画面を出す。
どこで何が失敗したかが書いてあり、原因を調べるのに使うからである。

テストでは、ステータスコードごとにエラー画面のページコンポーネントと正しいステータスコードが返ることと、`APP_DEBUG` が `true` のときは返さないことを確かめる。
書く前に、テスト環境の `APP_DEBUG`（`phpunit.xml`）を見ておく。
`true` のままだと詳しい画面のほうが返るので、テストの中で切り替える必要がある。

ここまでできたら、ブラウザで存在しない URL を開き、404 の画面が出ることを確かめる。

### 4. 通信失敗を知らせる

触るファイルは `resources/js/app.tsx` と、`resources/js/shared/lib/` に新しく作る1ファイルとそのテスト。

Inertia は通信で問題が起きるとイベントを発火する。
使うのは次の2つである。

- `inertia:networkError`：サーバに届かなかった
- `inertia:httpException`：Inertia 形式でない応答が返ってきた（Fly.io のプロキシが返す 502 など）

イベントを受け取ってトーストを出す処理を `shared/lib/` に書き、`app.tsx` で `router.on` を使ってつなぐ。
`app.tsx` に直接書かないのは、テストから呼び出せなくなるからである。

`httpException` のときは、Inertia が標準で英語のモーダルを出す。
`preventDefault()` でこれを止め、トーストだけにする。

トーストを表示する `Toaster` は、ログイン後の画面、ログイン画面、管理画面にすでにあるので、新しく置かなくてよい。

テストでは、2つのイベントでトーストが出ることと、モーダルが止まることを確かめる。
ブラウザでは、開発者ツールでオフラインにして購入を記録し、トーストが出てダイアログが残ることを確かめる。

### 5. 設計書を直す

触るファイルは `doc/design/non-functional.md`。

エラー画面の出し分けと、通信失敗のときの動きを書き足す。

### 6. まとめてブラウザで確かめる

手順3と4で確かめたものに加えて、次を試す。

- 他人のストックの編集画面を開くと、403 の画面が出る
- ログイン画面を長く開いたまま送信すると、419 の画面が出る
- 管理画面で存在しない URL を開くと、戻り先が管理画面のダッシュボードになる

## 採らなかった案

**419 では画面を出さず、元の画面に戻してトーストで知らせる。** 入力し直しの手間は減るが、戻った先では何が起きたか分かりにくい。
期限切れはめったに起きないので、デザインどおり画面で説明する。

**Laravel 標準のやり方（`resources/views/errors/` に画面を置く）で作る。** 画面の切り替えの途中でエラーが起きると、作った画面もモーダルの中に出てしまい、今の困りごとが残る。
