# 未読の通知をまとめて片付ける

## 目的

`20261101-improvement-backlog.md` の B4 に対応する。

購入予定日を過ぎたストックがあると、毎朝の通知が1件ずつ履歴に増える。
通知画面には未読だけが出るが、既読にするには1件ずつ押すしかない。
履歴は消されないので、テーブルは使い続けるほど大きくなる。
しかも通知画面の検索に使えるインデックスが無いので、行が増えるほど遅くなる。

backlog には「購入しても過去の未読が残る」も挙がっていたが、今回は扱わない。
超過中に未読が増えていくのは、一括既読で片付けてもらう。

## 決めたこと

- 未読をまとめて既読にするボタンを通知画面に置く
- 一括既読の後もトーストの「元に戻す」で戻せるようにする。1件ずつの既読と同じ操作感にする
- 作成から90日を過ぎた通知は、既読かどうかに関係なく消す。超過中は毎日新しい通知が届くので、3か月前の通知を残しても役に立たない
- 通知画面の検索に合わせたインデックスを足す

## 一括既読

### 何をするか

通知画面の「未読の通知」の見出しの横に「すべて既読」ボタンを置く。
未読が1件も無いときは出さない。

押すと `PATCH /notifications/read-all` を送る。
サーバは、ログイン中の利用者の未読を全部既読にする。
画面に出ている20件だけでなく、2ページ目以降の未読も対象にする。

### 元に戻すために、既読にしたIDを返す

「元に戻す」は、さっき既読にしたものだけを未読に戻す必要がある。
もともと既読だった古い通知まで未読に戻ってはいけない。
そこでサーバは、既読にした通知のIDを画面へ返す。

返すには Inertia の flash（次の1回の画面表示にだけ載せて渡すデータ）を使う。
コントローラで `Inertia::flash('readIds', $ids)` としてから `back()` を返すと、画面側では `router.patch` の `onFlash` で受け取れる。
受け取ったIDを持たせてトーストを出し、「元に戻す」が押されたら `PATCH /notifications/unread` にIDの配列を付けて送る。

### IDを先に取ってから更新する

サーバ側の処理は、「未読のIDを取る」と「そのIDを既読にする」の2段に分ける。

```php
$ids = NotificationLog::where('user_id', Auth::id())
    ->where('status', NotificationStatus::Unread)
    ->pluck('id');

NotificationLog::whereIn('id', $ids)->update(['status' => NotificationStatus::Read]);
```

「未読を全部既読にする」の1文で済ませてからIDを取り直すと、その間に9時の通知が1件増えた場合にずれが出る。
既読にした件数と、返すIDの一覧が食い違う。
先にIDを決めてしまえば、既読にしたものと「元に戻す」で戻すものが必ず一致する。

### 他人の通知を戻せないようにする

`PATCH /notifications/unread` は、画面から送られたIDの配列を受け取る。
IDは書き換えて送れるので、そのまま信じると他人の通知を未読にできてしまう。
更新の条件に `where('user_id', Auth::id())` を必ず付け、自分の通知以外のIDは何もせずに無視する。

1件ずつの既読は、URLの `{notificationLog}` から1件を取り出し（ルートモデルバインディング）、持ち主でなければ 403 を返している。
配列で受け取る場合は1件ずつ確かめる代わりに、この絞り込みで同じことを守る。

入力は `ids` が必須の配列で、中身は整数とする。

## 古い履歴を消す

`20261104-prune-unverified-users.md` で `User` に使ったモデルの刈り込みを、`NotificationLog` にも使う。

ただし、トレイトは `Prunable` ではなく `MassPrunable` にする。
`Prunable` は条件に合う行を1件ずつ取り出し、モデルのイベントを起こしながら消す。
`User` は消す前にほかのテーブルを片付ける必要があったので、それが要った。
通知の履歴には片付けるものが無いので、条件に合う行を `DELETE` 文でまとめて消す `MassPrunable` で足りる。
件数が多くても速い。

```php
use MassPrunable;

const RETENTION_DAYS = 90;

public function prunable(): Builder
{
    return static::where('created_at', '<=', now()->subDays(self::RETENTION_DAYS));
}
```

スケジュールは既存の3時の `model:prune` に相乗りさせ、`--model` を配列にする。

```php
Schedule::command('model:prune', ['--model' => [User::class, NotificationLog::class]])->dailyAt('03:00')->timezone('Asia/Tokyo')->onOneServer();
```

配列を渡すと `--model=... --model=...` と並べて渡される。

## インデックス

`notification_logs.user_id` には外部キー制約があるが、インデックスは無い。
`foreignId()->constrained()` は制約を作るだけで、PostgreSQL は外部キーにインデックスを自動では作らない（MySQL は作る）。

通知画面は「利用者で絞る、未読で絞る、作成日時の新しい順に並べる」の順で検索する。
一括既読も、利用者と未読で絞る。
これに合わせて `(user_id, status, created_at)` の複合インデックスを1本足す。

複合インデックスは、左の列から順に使われる。
利用者で絞った中を、さらに未読で絞った中は、作成日時の順に並んでいる。
そのため、絞り込みも並べ替えもインデックスだけで済む。

刈り込みは `created_at` だけで探すので、このインデックスは使えない。
ただ、90日で消すようにすればテーブルは大きくならず、1日1回の処理なので、刈り込み用のインデックスは足さない。

DB設計を変えるので、drawSQL の図にも足してエクスポートし直す。
